## Current State

The current constitution references markdownlint only as a one-line Additional Constraint bullet:

> `Markdown linted via markdownlint-cli2`

This is not an enforceable principle: it names the tool but does not state what passing means,
does not bind CI, does not specify how the ignore list is managed, and carries no severity level
in PR review.

## Proposed Change

### Principle: §VIII Markdown Quality (MUST)

Elevate the existing Additional Constraints bullet to a named, enforceable principle:

---

### §VIII Markdown Quality (MUST)

All markdown files committed to the repository MUST pass `npx markdownlint-cli2 "**/*.md"`
with zero errors against the project `.markdownlint-cli2.jsonc` configuration.

**MUST requirements:**

- Every markdown file merged to the default branch must produce zero markdownlint errors.
- The CI lint job (`.github/workflows/lint.yml`) must run on every push and pull request and
  must be required-to-pass before merge.
- Paths excluded via the `ignores` block in `.markdownlint-cli2.jsonc` must have a documented
  rationale comment in the config file (e.g., `// runtime artifacts — gitignored, not committed`).
- New `ignores` entries must be introduced in the same PR that introduces the excluded path pattern,
  not as a retroactive fix after CI failures.
- Runtime-generated markdown (e.g., `.documentation/devspark/runs/**`) MUST be excluded via the
  `ignores` block rather than fixed; runtime tooling is not responsible for linting its own output.

**SHOULD recommendations:**

- Run `npx markdownlint-cli2 "**/*.md"` locally before pushing (`npm run lint:md` if wired).
- Use editor integrations (VS Code markdownlint extension) for real-time feedback during authoring.
- Keep the `ignores` list minimal; prefer fixing files over excluding them.
- When a draft or in-progress document cannot pass lint yet, place it under a path already in
  `ignores` (e.g., `.documentation/drafts/`) rather than adding a new exclusion.

---

**Rationale**: The current one-line constraint is not actionable in PR review — reviewers cannot
cite a principle when lint violations appear, and contributors have no clear expectation. Elevating
this to a numbered MUST principle makes lint status a first-class PR gate with explicit severity
(HIGH) for violations that block CI.
