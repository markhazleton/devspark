# ADR-002: Delivery-Aware Harness Execution Model

## Status

Accepted

## Context

The DevSpark Harness could report end-to-end workflow completion even when no
implementation work occurred — a false-positive completion state that made
spec-to-pr-review automation unreliable. The root issue was a single `workflow_status`
field that encoded orchestration completion only, with no signal about whether
actual code or tests were produced.

Adapter readiness was also under-specified: an adapter registered in the adapter
registry might silently fail write operations in an unattended run, producing
unpredictable outcomes with no structured diagnostic.

## Decision

Introduce a dual outcome model (`workflow_status` + `delivery_status`) with a
derived `create_pr_ready` flag, governed by an evidence-based delivery gate:

1. **Dual Outcome Model** — `workflow_status` encodes orchestration; `delivery_status`
   encodes implementation evidence. `create_pr_ready` is blocked unless both pass.

2. **Delivery Evidence Default** — At least one changed file under `src/**` or
   `test/**` is required for implement-stage delivery success by default.

3. **Adapter Doctor** — Adapters expose explicit capability states
   (`available`, `read-only-works`, `write-approval-required`, `unusable`).
   Write-incompatible adapters fail fast on write-required stages.

4. **Convergence Loop** — Iterative analyze/critic re-validation runs up to 3
   passes per stage; a structured convergence failure report is persisted if
   blocking findings remain after all passes.

5. **Hands-Off Lifecycle Mode** — Optional single-run mode chains
   `plan → tasks → analyze → critic → implement → create-pr → pr-review` with
   hard gate enforcement and no human confirmation checkpoints mid-run.

6. **Decision Packet Artifacts** — Per-pass iteration records and a final
   decision packet (evidence summary, findings, recommendation) are persisted
   for auditability and downstream automation.

## Consequences

### Positive

- Eliminates false-positive "complete" runs that include no implementation changes
- Makes adapter write-capability failures explicit and actionable before work starts
- Provides deterministic iterative behavior with bounded retries (max 3 passes)
- Enables fully unattended end-to-end lifecycle execution
- Structured artifacts support debugging and reproducibility

### Negative

- Delivery gate introduces a new hard requirement: implement-stage specs must
  produce `src/` or `test/` changes (overridable per workflow YAML)
- Hands-off mode removes mid-run confirmation checkpoints, increasing risk of
  unreviewed changes reaching a PR if gate logic has gaps
- Convergence loop adds latency for specs with recurring findings
