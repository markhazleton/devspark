# ADR-001: Tiered Prompt and Workflow Architecture

## Status

Accepted

## Context

Through v2.0.0, DevSpark behaved primarily as a prompt library with partial orchestration patterns layered on top. Individual commands worked well in isolation, but there was no first-class, standardized workflow model that separated:

- **Atomic capability** (single-purpose prompts)
- **Orchestrated flow** (multi-step compositions)
- **Human-friendly entrypoints** (aliases)
- **Governance controls** (autonomy policy, gates)

This gap created operational friction: contributors had to manually stitch prompt sequences, consistency varied across lifecycle stages, autonomy boundaries were implicit, and observability signals were not standardized for workflow-level analysis.

The Harness Runtime (spec 002, shipped in v2.0.0) solved declarative *adapter-driven* execution but did not address the *prompt composition* layer. A complementary tier was required for the existing slash-command surface.

## Decision

Re-architect DevSpark into a **tiered system** with five explicit layers:

1. **Atomic prompts** — single-capability prompts (e.g., `/devspark.specify`, `/devspark.plan`)
2. **Workflow definitions** — YAML-declared compositions of atomic prompts (`templates/workflows/*.yaml`)
3. **Alias entrypoints** — human-friendly names that resolve to workflows (`templates/aliases/*.yaml`) — `create-spec`, `execute-plan`, `suggest-improvement`
4. **Autonomy policy** — declarative pause/resume gates and human-approval requirements
5. **Step-level observability** — telemetry events emitted by the runner (loader/executor/telemetry/autonomy modules)

Existing prompt behavior is preserved backward-compatible (28 legacy atomic shims auto-generated from canonical command prompts). The runner supports both assisted and autonomous modes through a shared execution contract.

The CLI surface adds: `devspark run`, `devspark resume`, `devspark workflows`, `devspark runs`, `devspark help`.

## Consequences

### Positive

- **Composability**: Workflows are now declarative artifacts, reviewable and testable independently.
- **Consistency**: A single execution contract ensures every workflow handles autonomy, telemetry, and pause/resume identically.
- **Backward compatibility**: All existing slash commands continue to work via auto-generated shims (Constitution Principle I).
- **Discoverability**: `devspark workflows` and `devspark help` give users a single place to find available compositions.
- **Observability**: Standardized telemetry events enable workflow-level analytics (success rates, time-to-completion, failure modes per step).
- **Issue-driven workflows**: GitHub issue adapter bridges issues into workflow inputs, enabling fully external orchestration.

### Negative

- **Two parallel execution layers**: Workflow runner (this ADR) and Harness Runtime (ADR-002 forthcoming, originally spec 002) are conceptually similar but target different domains. Future consolidation may be warranted; complexity must be tracked per Constitution Principle V (Simplicity).
- **Schema maintenance burden**: Workflow YAML schema, alias YAML schema, and atomic prompt frontmatter contracts must stay in sync as each evolves.
- **Shim drift risk**: 28 generated atomic shims must regenerate cleanly whenever canonical prompts change; a CI check (`shim-drift.yml`) was added but adds a maintenance gate.
